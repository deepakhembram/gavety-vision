# Gavety Vision — full Docker edition

All CCTV logic now runs in Docker. The agent binary no longer contains any camera / Frigate / AI code.

```
Dashboard ──► agent (Go binary)            thin bridge only: vision_manager.go (~250 lines)
                 │  HTTP, 127.0.0.1:5160, bearer token
                 ▼
          gavety_vision_core  (container, NEW)    devices, Frigate config, resolution detection,
                 │  docker.sock                    storage limits, AI hazard layer, events
                 ▼
          gavety_vision  (Frigate container, unchanged name / port 5150 / label)
                 ▲
          AI worker (optional container: Pi, laptop GPU, or cloud GPU)  ◄── POST /v1/analyze
```

Nothing changes for the dashboard: same WebSocket commands, same reply messages, same state files
(`/etc/gavety/vision_devices.json`, `vision_settings.json`, `vision_config.yml`), same Frigate
container name/port, so existing installs carry over.

## Folder

| Path | What |
|---|---|
| `core/` | The new container (Go). `Dockerfile`, source, tests. |
| `agent_shim/vision_manager.go` | **Replaces** the agent's `vision_manager.go`. |
| `worker/` | AI worker container (unchanged from the earlier delivery). |
| `compose/` | `docker-compose.yml` + `.env.example` to run everything without the agent. |
| `.github/workflows/docker-publish.yml` | Test + build + push to **Docker Hub and GHCR** (core: amd64+arm64, worker: amd64). |

## Test it — in this order

### 1. Core alone, on your Windows PC (Docker Desktop), no agent, no Pi
You need a camera or DVR reachable on your LAN.
```
cd vision_docker
docker build -t gavety-vision-core:dev core
cd compose
copy .env.example .env        (edit: CORE_IMAGE=gavety-vision-core:dev, GAVETY_CORE_TOKEN=<16+ chars>)
docker compose up -d vision-core
```
On Windows the paths `/etc/gavety` and `/mnt/gavety_storage` mean folders inside Docker Desktop's WSL;
for this quick test it is simplest to run step 1 on the Pi (same commands) or set `STATE_DIR` / `HDD_ROOT` to
WSL paths such as `/home/<you>/gavety/state`.

Then (replace TOKEN):
```
curl -H "Authorization: Bearer TOKEN" http://127.0.0.1:5160/v1/info
curl -X POST -H "Authorization: Bearer TOKEN" -d "{\"ip\":\"CAM_IP\",\"username\":\"admin\",\"password\":\"PASS\"}" http://127.0.0.1:5160/v1/devices/test
curl -X POST -H "Authorization: Bearer TOKEN" -d "{\"nickname\":\"Gate\",\"ip\":\"CAM_IP\",\"username\":\"admin\",\"password\":\"PASS\"}" http://127.0.0.1:5160/v1/devices
curl -X POST -H "Authorization: Bearer TOKEN" http://127.0.0.1:5160/v1/apply
```
Expected: `Connection successful`, `device saved`, and after ~15 s `Gavety Vision is ready`; Frigate UI on `http://localhost:5150`.

### 2. On the Raspberry Pi with the real agent
1. Back up: `cp vision_manager.go vision_manager.go.bak` in the agent source.
2. Copy `agent_shim/vision_manager.go` over it. **No other agent file changes.**
3. Get the core image onto the Pi: pushed from CI (step 3) **or** `docker build` on the Pi, or
   `docker save | ssh | docker load` from your PC (use `--platform linux/arm64` when building on the PC).
4. Build the agent with your image name:
   `go build -ldflags "-X main.visionCoreImage=deepakdipu/gavety-vision-core:<tag>"`
5. Restart the agent. Open Gavety Vision in the dashboard: list / add / test / delete camera, change storage drive.
   `docker ps` should show **`gavety_vision_core`** and **`gavety_vision`**; the app list must still show only
   *one* Vision app (the core has no `gavety.managed` label on purpose).

### 3. Publish to Docker Hub and GitHub
1. Push `vision_docker/` to a GitHub repo.
2. Repo → Settings → Secrets and variables → Actions:
   variable `DOCKERHUB_NAMESPACE`; secrets `DOCKERHUB_USERNAME`, `DOCKERHUB_TOKEN`.
3. `git tag v0.1.0 && git push origin v0.1.0` → images appear on Docker Hub and `ghcr.io/<owner>/…`.
   Pull requests only build and test (no push).
   Make the GHCR package public (Package settings) if the Pi should pull without logging in.

## Rollback
Restore `vision_manager.go.bak`, rebuild the agent, `docker rm -f gavety_vision_core`. State files are
untouched by the Docker edition, so the old binary continues with the same cameras.

## Optional one-line edit (not required)
When someone uninstalls the Vision app, the core container is not removed (it is idle, harmless).
To remove it together, in `docker_manager.go` `handleDockerRemove`, inside/after the
`if appID == "vision" && removeVolumes {` block add:
```go
if appID == "vision" { exec.Command("docker", "rm", "-f", "gavety_vision_core").Run() }
```

## Security notes
- The core mounts `/var/run/docker.sock` (root-equivalent). Its API listens on `127.0.0.1` only, needs a bearer
  token (auto-generated by the agent into `/etc/gavety/vision_core_token`, mode 0600) and refuses to start without one.
- Camera passwords stay in `vision_devices.json` (0600) and are never returned by the API.

## Updating the core without rebuilding the agent (app catalog)
The Vision entry in `aws/app-catalog.json` can carry the core image:
```json
{ "id": "vision", ..., "companion_image": "deepakdipu/gavety-vision-core:0.1.0" }
```
Two small edits in the agent's `docker_manager.go`:
```go
// 1. in type CatalogApp
CompanionImage string `json:"companion_image,omitempty"`

// 2. in fetchAppCatalog(), right after appCatalogMu.Unlock()
for _, a := range result.Apps {
	if a.ID == "vision" { visionApplyCatalogImage(a.CompanionImage) }
}
```
On each catalog refresh (hourly) the bridge pulls the new image **first**, remembers it in
`/etc/gavety/vision_core_image`, and restarts only the core (Frigate and recordings are not touched).
A failed pull changes nothing and is retried next hour. Without the field, the built-in default is used.
The AWS backend needs no code change: it serves the catalog file as-is.

## Hybrid: the same Vision page on the Pi **and** on any PC (standalone mode)
The core can serve the Vision page itself, with its own password login. It is **off by default**:
on a Gavety box nothing changes (the dashboard opens the page and the agent forwards commands).

| | Pi / Gavety box | Any PC with Docker |
|---|---|---|
| Who serves the page | the agent (dashboard popup) | the core container, `http://<pc>:5170` |
| Login | dashboard login | own password (first-run setup code, or `GAVETY_UI_PASSWORD`) |
| Camera/Frigate | same core + Frigate containers | same core + Frigate containers |

**Run on a PC:**
```
cd compose
copy .env.standalone.example .env
docker compose -f docker-compose.standalone.yml up -d
docker logs gavety_vision_core        (find the setup code)
```
Open `http://localhost:5170`, set a password, add a camera. Live view and recordings go through a read-only,
allow-listed proxy to Frigate (Frigate's `/api/config` holds camera passwords and is never exposed).

Settings (environment): `GAVETY_UI_ADDR` (enables the page, e.g. `0.0.0.0:5170`), `GAVETY_UI_PASSWORD`,
`GAVETY_FRIGATE_URL` (default `http://127.0.0.1:5150`; use `http://host.docker.internal:5150` on a PC).

Security notes: the page is plain HTTP, so use it on a trusted LAN or behind a VPN/reverse proxy; passwords are
stored as PBKDF2-SHA256; sessions are HttpOnly + SameSite=Strict cookies; 5 failed logins/minute/address are
blocked; the setup code stops a stranger on your LAN from claiming a fresh install.

`vision.html` is ONE file used in both modes (`core/ui/vision.html`; copy it to the agent's `opt/vision.html`).

**Windows note (not verified on a real Docker Desktop):** `DATA_DIR` (default `/srv/gavety`) is a path inside
Docker's Linux VM, so recordings live in Docker's disk image, not on `C:`. Check free space for long retention.
